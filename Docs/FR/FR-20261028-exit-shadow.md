# FR-20261028-exit-shadow：影子離場訊號（只記錄、不賣）

- 狀態：active（本機完成，114 個測試通過，主機 Python 3.12 也全過；尚未部署）
- 來源：fish 10-28：「加一個只記錄、不真的賣的離場訊號……累積到 11-02 再看」；「關鍵是速度」

## 1. 改了什麼
`sim.py`：進場後的最後 60 秒，每一輪判斷都用官方規則算一次「還能贏的機率」。結算價 = 最後 60 秒 Chainlink 每秒價格的平均：已經公布的秒數用實際價格，還沒公布的用 Coinbase 現價加上價差，剩下的不確定性用這場的每秒波動估。記在 `sim_exit.csv`：
- `lag`：第一次出現「勝率 < 0.3，而且我方賣價（1 − 對面賣價）仍 ≥ 0.5」的時刻，也就是市場還沒反應過來的時候。
- `p10`：第一次勝率 < 0.1 的時刻。
- 每一筆記下當下的勝率、偏向、不確定度、賣價，以及 **0.5 秒、1 秒、2 秒後的賣價**（量出速度值多少錢），結算後補上輸贏、抱到結算的每股淨利、在那一刻賣的每股淨利。

開關 `EXIT_SHADOW`（預設開），門檻 `EXIT_P`（0.3）、`EXIT_MIN_BID`（0.5）。出現 `lag` 訊號時，journal 會記一行 `shadow exit (no order)`。

## 2. 為什麼
歷史研究（`Docs/custom-queries/exit_on_reversal.py`）：一般停損都比抱到結算差。只有「模型說輸、賣價還 ≥0.5」這一種是正的，但只有 12 次、4 筆輸單。歷史資料只能用 Coinbase 推估官方價格，盤口每 0.5 秒才一筆，速度的價值可能被低估。所以改用官方即時資料，照實際判斷速度記錄。

## 3. 修改前
沒有任何離場判斷，一律抱到結算。

## 4. 修改後
交易行為完全不變，仍然抱到結算。只是多寫一個紀錄檔，journal 多一行訊息。

## 5. 影響檔案
`btc5m_sim/sim.py`（`EXIT_*` 設定、`cl_sigma_bps`、`win_prob`、`exit_rows`、迴圈內的檢查、`sim_exit.csv`），`tests/test_btc5m_sim.py`（ShadowExit ×2）。

## 6. 對交易、下單、風控、資料判斷的影響
**不送任何單、不改任何決策**。檢查包在 try 裡面，出錯只記一次 log，不會影響當輪判斷。每輪多一點計算（最多 120 個價格點），成本可忽略。

## 7. 驗證與驗收邊界
部署後，在出現第一筆進場而且行情反轉的場次，`sim_exit.csv` 應該有列。11-02 用它算：`lag` 訊號觸發時賣，跟抱到結算比，扣手續費後是不是正的；`bid_05s／1s／2s` 和 `bid` 差多少，就是速度的價值。

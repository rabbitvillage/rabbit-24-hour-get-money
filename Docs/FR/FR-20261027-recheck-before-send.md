# FR-20261027-recheck-before-send：送單前再看一次盤口，領先方崩掉就不買

- 狀態：active（fish 10-27 19:2x 裁示部署；19:30:06 主機 daeba31、四服務 active。19:54:00 第一次動作：`live aborted w60_m95_s20 ... Down: ask rose 0.94 -> 0.98 above limit 0.96 before post`，簽名花了 1,001 ms，省掉一筆必然 no-match 的單；「掉 ≥0.05 擋下」的樣本還沒出現，出現後轉 verified）
- 起因：2026-10-27 18:34 BTC 真單「決定在 0.84、成交在 0.57」，輸 $7.90。

## 1. 這次改了什麼

`live.py` 的送單執行緒在兩個時間點用 websocket『即時推送』盤口再看一次領先方的最佳賣價（不打網路，約 0 ms）：簽名前、以及簽好名要 POST 前。只要賣價比規則決定時看到的低 ≥ `LIVE_RECHECK_DROP`（預設 0.05）—— 代表這一邊正在崩 —— 或低於 `LIVE_RECHECK_FLOOR`（預設 0.80，fish 10-27：「80～97 可以接受，50 太離譜」），或已經高過送單上限（ask + SLIP = 最高 0.97），就不送單，帳本記 `status=aborted`『取消』。`sim.py` 把每個 token 的「現在最佳賣價」函式（`ask_now`）傳給 `live.submit`。`LIVE_RECHECK_DROP=0` 關閉。

## 2. 為什麼要改

FAK『成交多少算多少，剩下取消』市價買單只有上限（ask + SLIP）沒有下限：交易所會把整筆 USDC 吃到上限以下所有賣單。18:34 的單：剩 36.6 秒看到 Down 賣價 0.84（距離 −21.3、振幅 4.6 bps，所有過濾都通過），送 8.92 股上限 0.86 = $7.67；0.95 秒後撮合時 Down 的賣單已經崩到 0.45～0.57，交易所用 $7.67 吃到 0.45～0.86 的所有賣單，均價 0.57、13.46 股。收盤 Up（Chainlink 收盤只高開盤 $1.5），−$7.67 − 手續費 $0.23。

這不是單一事件。661 筆真單（10-19～10-27）按「成交均價 − 決定時賣價」分組（`Docs/custom-queries/fill_discount.py`）：

| 成交 vs 看到的賣價 | 筆數 | 輸 | 毛利 |
|---|---|---|---|
| 便宜 ≥ 0.15 | 18 | 8（44%） | −$18.79 |
| 便宜 0.05～0.15 | 36 | 6（17%） | −$13.94 |
| 便宜 0.01～0.05 | 122 | 12（10%） | −$14.94 |
| 原價 | 282 | 4（1.4%） | +$52.76 |
| 貴（+1～2 分） | 203 | 6（3%） | +$39.98 |

便宜成交就是逆向選擇：成交能比看到的便宜，只因為那一邊在這 1 秒內正在崩。用機器人自己每 0.5 秒的盤口紀錄當「送單前再看一次」的代理（決定後 0.9 秒的賣價 − 決定時賣價）：629 筆可對照的單裡，掉 ≥0.05 的 28 筆會被擋（9 輸 19 贏，合計 −$25.69）；掉 0.01～0.05 的 114 筆（11 輸，+$1.92）不擋；沒動或變貴的 487 筆（14 輸，+$75.82）不受影響。

## 3. 修改前的行為

決定後只在 guard『送單前檢查』看規則、價位帶、每場上限、冷卻、餘額；簽名 0.5 秒、送單 0.35 秒之間不再看盤口。盤口崩掉時 FAK 照樣成交，而且因為價格變便宜，買到的股數更多。

## 4. 修改後的行為

簽名前、POST 前各看一次 ws 盤口；領先方賣價掉 ≥0.05 或高過上限就不送，`live_orders.csv` 記一列 `aborted`，`live_timing.csv` 也記時序，journal 有 `live aborted ...` 行。aborted 不佔「每場 1 筆」名額（另一條真單規則之後還能進場），但同一條規則同一場不會再試（原本就一場一次）。dry『模擬』模式也一樣會記 aborted。沒有 ws 盤口（REST 退回、盤口過舊）時不檢查，照原本送。

## 5. 影響的檔案

- `btc5m_sim/live.py`：`RECHECK_DROP`、`RECHECK_FLOOR`、`_book_moved()`、`submit()/_submit()` 多一個 `book_fn` 參數、兩處再檢查。
- 擋不住的部分（要誠實）：最後一次檢查之後還有約 0.35 秒的送單＋撮合時間；在那 0.35 秒內才崩的盤口，成交仍可能便宜。18:34 那筆從 0.84 掉到 0.73 花了 0.4 秒、到 0.57 花了 0.9 秒，兩個檢查點都會擋住；更快的崩盤沒有客戶端辦法，只能靠決定前的過濾（todo 第 13 項）。
- `btc5m_sim/sim.py`：`ask_now()`，兩處 `live.submit(...)` 傳 `book_fn`。
- `tests/test_btc5m_live.py`：三個新測試（POST 前擋住崩盤、簽名前擋住跑高、關閉開關；dry 也記 aborted）。
- `Docs/custom-queries/fill_discount.py`、`book_gap_filter.py`：證據腳本。

## 6. 對交易、下單、風控、資料判斷的影響

- 會**少送**一部分單（歷史重放約 4%，28/629），其中三分之一是輸單；不會多送任何單。每筆上限、股數、價位帶、距離、震盪、冷卻、停損全部不變。
- 預期：每天少 1～2 筆成交，少掉的那組歷史上合計是負的。
- 不改的部分：決定前的過濾（這筆單所有過濾都通過了），因為「兩邊賣價和 >1.05 的盤口不買」是策略層的改動，見 todo 第 13 項。

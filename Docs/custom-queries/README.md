# 客製化查詢指令（custom queries）

這裡放可以重複跑的分析腳本。全部**唯讀**：只讀 `btc5m_sim/data*/` 的 CSV 和 Polymarket 公開的 data-api『公開資料介面』，不碰 `.env`、不下單、不改主機。標準函式庫就能跑，不用裝套件。

資料在主機上，所以通常是把這個資料夾 `scp` 到主機 `/tmp/cq/` 再跑：

```bash
scp -P 22888 Docs/custom-queries/*.py root@100.75.171.83:/tmp/cq/
```

需要錢包地址的腳本，用機器人自己的 identity『身分查詢』拿代理錢包地址（公開地址，不含金鑰）：

```bash
cd /opt/rabbit-24-hour-get-money && set -a; . btc5m_sim/.env; . btc5m_sim/.live.env; set +a
W=$(python3 -c 'import btc5m_sim.live as L; print(L.identity()["proxyWallet"])' | tail -1)
```

data-api 每分鐘抓太多會回 429『請求太多』，腳本已經每頁停 1.5 秒並自動重試；同一分鐘內不要連跑兩支抓鏈上的腳本。

共用模組：`polyaudit_lib.py`（抓 activity、讀機器人帳本、把鏈上成交配對到機器人訂單）。配對規則是 slug＋方向＋時間 ±300 秒＋股數相符；只用 slug＋方向配會把手操買同一邊的單算成機器人的。

## audit_chain.py：手續費與手操稽核

- **用途**：對帳。算機器人每筆真單在鏈上實際付的手續費（帳本記 0），以及不屬於機器人的加密盤手操按日、按買價的損益。
- **參數**：`<代理錢包地址> <repo 根目錄> [最多抓幾列，預設 6000]`
- **怎麼跑**：`python3 -I /tmp/cq/audit_chain.py "$W" /opt/rabbit-24-hour-get-money`
- **怎麼看**：`fee paid on those fills` 是真單總手續費；`ledger pnl ... -> after fees` 才是真正損益。手操表的 P&L = 賣出 + 結算領回 − 買進（手續費已含在買進金額裡）。`not found on chain` 是帳本有、鏈上沒抓到的單（通常是超出抓取範圍）。
- **不能拿去下單的情況**：這是事後對帳，不是訊號。手操的輸贏是當天的結果，不代表方法有優勢；樣本少於幾百筆時 ±10% 都是雜訊。

## manual_day.py：某一天的手操逐場檢視

- **用途**：把某一天（台灣時間）的手操一場一場列出來，旁邊放機器人自己錄到的行情：收盤時離開盤價幾 bps、最後 150 秒領先方換邊幾次、剩 120 秒時的領先方最後有沒有贏。可用 `split` 把一天切成前後兩段比較「做得上去」和「崩掉」的時段行情有沒有差。
- **參數**：`<代理錢包地址> <repo 根目錄> <YYYY-MM-DD> [切分時間 HH:MM] [幣 btc/eth/sol，預設 btc]`
- **怎麼跑**：`python3 -I /tmp/cq/manual_day.py "$W" /opt/rabbit-24-hour-get-money 2026-10-24 19:05 btc`
- **怎麼看**：`fav/dog` = 第一筆買的是領先方還是落後方；`held` = 有部位抱到結算；`both` = 同一場兩邊都買過；`entry_s` = 第一筆買進距離收盤幾秒；`flips` = 最後 150 秒領先方換邊次數；`lead120` = 剩 120 秒的領先方最後贏了沒；`move_bps` = 收盤價離開盤價幾 bps。下方 `[before/after]` 是兩段的手操統計和「該時段所有場次」的行情統計。
- **不能拿去下單的情況**：一天幾十場分不出技術和運氣（每場 $20 的賭注，36 場的隨機波動一個標準差約 ±$85）。行情統計是事後看的，收盤前不知道。

## flip98.py：0.98～0.99 進場後翻船率

- **用途**：假設最後 N 秒內領先方賣價一到 0.98～0.99 就買，統計翻船率（買的那邊輸）和每股損益（未扣手續費），分美股時段／非美股時段。
- **參數**：一個或多個資料夾 `btc5m_sim/data btc5m_sim/data-eth btc5m_sim/data-sol`
- **怎麼跑**：`cd /opt/rabbit-24-hour-get-money/btc5m_sim && python3 -I /tmp/cq/flip98.py data data-eth data-sol`
- **怎麼看**：買 0.98 要賺錢，翻船率要低於約 1.86%（扣手續費後）；買 0.99 要低於 0.93%。表下方列出每一次翻船的場次。
- **不能拿去下單的情況**：它假設看到賣價就買得到；真單約 16% 會貴 1 分，而且有逆向選擇（能成交的常是快翻的）。翻船樣本只有個位數時，±1% 都是誤差。

## tail98.py：專吃 0.97／0.98 的期望值

- **用途**：假設只在最後 60／45／30 秒、領先方賣價剛好 0.97 或 0.98、掛單夠深時買，算每天機會次數、翻船率、扣手續費後每股期望值，以及貴 1 分成交時的期望值。
- **參數**：同 flip98.py
- **怎麼跑**：`python3 -I /tmp/cq/tail98.py data data-eth data-sol`
- **怎麼看**：`ev/share` 是扣手續費（7%×p×(1−p)）後每股期望值（分）；`worse1c` 是成交貴 1 分時的期望值。正的才有肉。`n/day` 是頻率。
- **不能拿去下單的情況**：2026-10-26 跑的結果，BTC 0.97 最後 45 秒每股約 +1 分，但翻船只有 6 次樣本（95% 區間跨過損益兩平），要再累積至少一個月資料重跑才能決定。

## real_orders_by_ask.py：真單按看到的賣價分組

- **用途**：機器人真單（已成交已結算）按決定時看到的賣價分組：筆數、勝率、帳本損益、成本、報酬率、成交價和賣價的平均差。
- **參數**：資料夾，例如 `data data-sol data-eth`
- **怎麼跑**：`python3 -I /tmp/cq/real_orders_by_ask.py data data-sol data-eth`
- **怎麼看**：`ret` 是帳本報酬率，**沒扣手續費**（0.98 約 0.14%、0.90 約 0.63%，用 audit_chain.py 的數字扣）。`avg(fill-ask)` 負數表示平均成交比看到的便宜，但會被翻盤後成交的極端值拉低，看分布請用 fill_slip_hist.py。
- **不能拿去下單的情況**：每個價位幾十筆，一筆輸單就改變結論。

## loss_streaks.py：真單連輸的日子，現在的設定還會不會發生

- **用途**：把所有真單（live_orders 成交 × live_results 結算）按時間排，找出連輸 ≥N 筆的段落；對每一筆輸單用「現在的」設定重放：ETH 已停、美股時段停單、0.80～0.95 價位帶與 60 秒窗口、方向＋距離過濾、震盪過濾、輸單冷卻、每場一筆、事件行事曆，列出哪些會擋、哪些「現在也會進場」。重放是循序的：只有現在會進場的輸單才會啟動冷卻、佔掉同場名額。
- **參數**：`[連輸門檻，預設 3]`；參數從環境讀（先 `set -a; . btc5m_sim/.env; set +a`，SOL 距離倍率用 `DIST_SCALE_SOL=0.004`）。
- **怎麼跑**：`cd /opt/rabbit-24-hour-get-money && python3 Docs/custom-queries/loss_streaks.py 3`
- **怎麼看**：每段連輸列出每筆的規則、賣價、成交價、剩秒、距離、振幅、損益，`|` 後面是現在會擋的原因；`★ 現在也會進場` 就是現在的設定擋不住的那種輸單。最後有全部輸單的統計。2026-10-27 跑：35 筆輸單中 33 筆現在會被擋，2 筆（10-26 10:59、13:49，BTC w60 非美股時段的尾盤翻船）現在也會進場。
- **不能拿去下單的情況**：這是用歷史資料重放今天的規則，資料有缺（10-20 前 BTC 沒距離紀錄）時會寫「沒有距離資料」；它證明的是「過去那種連輸的原因已經不在」，不是「以後不會輸」。

## day_regime.py：今天是好行情還是正常行情

- **用途**：回答「今天賺是因為行情好，還是正常日？」。每個台灣日、每幣兩個視窗（同時段 05:00～16:30，也就是當天已經跑過的非美股時段；以及整個非美股時段）列出：場數、收盤離開盤價中位數（bps）、最後 150 秒幣價振幅中位數、剩 60 秒領先方最後輸掉的比例（flip60）、機器人的「局」出現率（剩 60 秒領先方賣價 0.80～0.95）和那種局的翻船率（setupflip）、真單規則的影子帳（進場／贏／輸／每 $1 報酬，未扣手續費）、當天真單（送出／成交／贏／輸／毛利）。
- **參數**：`[HH:MM-HH:MM]`（預設 05:00-16:30）`[規則名]`（預設 `LIVE_VARIANTS` 第一個，先 `set -a; . btc5m_sim/.env; set +a`）
- **怎麼跑**：`cd /opt/rabbit-24-hour-get-money && python3 -I Docs/custom-queries/day_regime.py`
- **怎麼看**：把今天那一列和前面幾天比。`setupflip` 是這套策略真正的風險指標：0% 是好日（10-23），20% 以上是壞日（10-26）；`med|move|` 7 以上、`flip60` 10% 以上是震盪日。影子帳 `lost` 多數日子是 0，所以「全贏」是這條規則的正常日，不是好日。2026-10-27 跑：BTC 05～16 時 132 場、|move| 5.0、flip60 6.8%、setupflip 8.0%，都在前 8 天的中間 → 正常日；SOL flip60 11.6%、setupflip 24% 偏震盪，影子規則 0 進場。
- **不能拿去下單的情況**：事後統計，收盤前不知道今天是哪種日子；一天十幾筆影子進場，一筆輸就把 `ret/$1` 從 +13% 拉到 +5%。

- **參數**：無；`REPO`『repo 根目錄』環境變數預設 `/opt/rabbit-24-hour-get-money`。
- **怎麼跑**：`python3 -I Docs/custom-queries/fill_discount.py`
- **怎麼看**：2026-10-27 跑（661 筆）：便宜 ≥0.05 的 54 筆輸 14（−$32.7），原價或貴的 485 筆輸 10（+$92.7）。便宜成交 = 那一邊正在崩 = 逆向選擇。代理重放：決定後 0.9 秒賣價掉 ≥0.05 的 28 筆（9 輸 19 贏，−$25.7）就是 FR-20261027-recheck-before-send 會擋掉的那組。
- **不能拿去下單的情況**：0.5 秒的盤口紀錄只是代理，實際再檢查看的是當下的 ws 盤口；分組裡輸單只有幾筆到十幾筆。

## twap_vs_coinbase.py：Coinbase 會不會變成官方結算價（歷史逐場）

- **用途**：官方結算規則是 Chainlink 的 60 秒 TWAP『時間加權平均價』：開盤價 = 開盤前 60 秒平均（= 上一場的 finalPrice），收盤價 = 最後 60 秒平均。用機器人記錄的 Coinbase 價格（sim_book.csv 最後 150 秒每 0.5～1 秒一筆）重算同一段的 Coinbase 平均，回答：(1) Coinbase 和官方差多少、穩不穩；(2) 只看 Coinbase 能不能猜中官方輸贏，和機器人現在的算法（Coinbase 即時價 − Polygon 鏈上喂價開盤價）比；(3) 剩 s 秒時用「已經過的平均＋現在價格補剩下的」預測，和當下盤口賣價比；(4) 兩條真單規則的影子進場，輸單在進場當下 TWAP 是否已經看得出來。
- **參數**：資料夾（在 btc5m_sim/ 底下跑，預設 data）；`DIST_SCALE`（BTC 不用設，SOL 設 0.004，對應機器人的 $20 距離規則）；`RULES`（預設 `w60_m95_s20,w45_m95_s20`）。
- **怎麼跑**：`cd /opt/rabbit-24-hour-get-money/btc5m_sim && python3 -I /tmp/cq/twap_vs_coinbase.py data`；SOL：`DIST_SCALE=0.004 python3 -I /tmp/cq/twap_vs_coinbase.py data-sol`
- **怎麼看**：單位 bps＝價格的 0.01%（BTC 約 $8）。2026-10-28 跑（BTC 2,458 場、SOL 1,586 場）：
  - Coinbase 平均比官方低一點：BTC 中位數 −0.41 bps（約 −$3.4），而且很穩：相鄰兩場的差距變化 |p50| 0.30、|p90| 0.80 bps。
  - 機器人現在的開盤基準線（Polygon 鏈上喂價）和官方開盤價差 |p50| 0.58、|p90| 2.32 bps（BTC 約 $19，幾乎等於 $20 距離門檻）。
  - 猜中官方輸贏（收盤時）：Coinbase 開收盤都用 60 秒平均 BTC 97.6%／SOL 98.2%；機器人的算法 91.1%／91.4%。差距最大的是勢均力敵的場次（官方漲跌 < $20）：剩 30 秒時 TWAP 算法 BTC 88.4%、機器人算法 79.0%。
  - **但在機器人的價位帶（賣價 0.80～0.95）裡，市場已經把 TWAP 資訊算進價格**：按 TWAP 偏向分組，勝率減賣價大多在 ±0.03 內（雜訊）。剩 30 秒以內，大部分場次領先方賣價已經 ≥0.95，落在價位帶的場次很少。

- **加自動對沖（10-29，fish：「要搭上自動對沖砍倉」）**：`HEDGE_T`＝只成交一邊後 T 秒另一邊沒成交就市價買另一邊；`HEDGE_D`＝成交那邊的賣價再跌 D 就市價對沖。結果（BTC 1,073 次、btc15 106 次、SOL 766 次）：對沖後虧損變小，但仍全部為負：立刻對沖每 $1 −5.3%～−7.1%，等 1～10 秒 −5.9%～−8.0%，跌 0.01～0.05 才對沖 −5.3%～−7.4%。每次對沖平均虧 6～16 分；越晚對沖虧越多。原因：買單被吃到的那一刻，另一邊已經漲上去，對沖價格已經不利。資料粒度 0.5～1 秒，實際對沖若能在 0.3 秒內完成，虧損會略小但不會翻正。

## two_sided_requote.py：兩邊掛單、每 3 秒撤掉重掛（兩張都沒成交才撤）

- **用途**：fish 10-29：Up 掛 0.45、Down 掛 0.50 這種組合，3 秒內兩張都沒成交就撤單重掛；有一邊成交就不撤，另一張繼續等，可再加自動對沖（`HEDGE_T`、`HEDGE_D`）。`REQUOTE`（秒）、`BAL`（只在兩邊價差 ≤ BAL 時掛）、`SUMS`（兩張合計價格）。

- **怎麼看**：2026-10-29（BTC 1,073～1,373 次、btc15 106～138 次、SOL 766 次）：全部為負。不對沖每 $1 −8%～−13%；成交一邊立刻對沖 −4.7%～−7.3%；3 秒後對沖 −5.6%～−8%；跌 3 分才對沖 −4.6%～−7.4%。和不重掛的版本（two_sided_maker.py）幾乎一樣：重掛讓掛單價跟著市場走，但被吃到的仍是正在往下掉的那一邊，「單邊成交、那邊最後贏」仍是 0 次。

## pair_open_replay.py：用開盤盤口記錄（pair_sim）回放「開盤後分兩次買兩邊」

- **用途**：fish 10-29 的做法：開盤 50／50 後兩邊擺動，先後各買一邊，扣兩邊手續費後合計仍 < $1。讀 `/opt/pm-pair/data/book_<幣>_<日>.csv`（只用完整錄到的場次），算：事後看是否每場都有機會、最早第幾秒做得到；以及三種事前就能執行的規則——A 先買正在跌的那邊（賣價 ≤ L1）、B 開盤前 5 秒用 0.50／0.51 先買 Up、C 先買正在漲的那邊（賣價 ≥ H1）——補到另一邊的比例和損益。兩邊都要求最佳價至少 `MIN_SZ` 股。
- **怎麼跑**：`cd /opt/pm-pair/data && python3 -I ../pair_open_replay.py btc eth sol`；`MARGIN`（扣費後每對至少賺多少，預設 0.01）、`MIN_SZ`（60）、`L1`（0.45）、`H1`（0.58）。
- **怎麼看**：10-29 21:15～22:15 第一小時（每幣 9 場完整場次）：事後看 **9／9 場都有**扣費後仍賺的組合（BTC 中位數開盤後 4 秒就湊得到，最好的一對合計中位數 0.95）。事前規則：B（開盤前買 Up）BTC 9／9 補成對、每 $1 +2.4%（每對至少賺 3 分時 +4.7%），ETH +2.6%／+4.1%，SOL −3.1%／−7.1%（9 場裡 1～2 場補不到）；A 約打平；C 明顯虧。
